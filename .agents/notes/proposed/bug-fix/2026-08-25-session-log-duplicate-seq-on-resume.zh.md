# Agent Note: 会话日志续写在恢复后复用了陈旧的 seq

Status: proposed

[English](2026-08-25-session-log-duplicate-seq-on-resume.md) | 中文

## 问题

JSONL 会话后端（`packages/session/session-persistence-jsonl`）用单调递增的 `seq` 给事件编号，读取方要求它等于已提交事件的运行计数：`src/format.ts` 的 `SessionLogScanner.consumeEventLine` 在某条记录的事件 seq 不匹配时抛出 `corrupt session log: seq gap in committed region`，并把抛出推迟到下一个 `turn/end`。因此一个重复的 seq 就会让整个会话不可读，其聊天历史永远加载不出来。

`src/index.ts` 的 `appendLines` 在写入或 sync 失败时会恢复文件的原大小，"因为……留下部分字节会造成重复的序号"，但这个回滚只覆盖单个进程内某个写入方自己的部分写入。当一个已在 seq N 封存了 `session/end-seed` 的会话被恢复——新的用户轮次拼接了一条 inbox 消息——第二个写入方可能提交一条复用了 seq N（而非 N+1）的 `agent/inbox/spliced` 记录。两个窗口分别是：并发的 `dsh web` 重启接管了同一个会话目录，以及在某一帧 fsync 与内存游标推进之间发生的崩溃。随后的 `turn/start` 取到 N+1，之后每个事件的编号都当作那个重复项从未占用过槽位，所以该重复项是一条多余的已提交记录，而不是尾部的整体位移。

在 `~/.dsh/sessions/` 下的 `session-5dc100c1-f981-42db-9787-d1c057824593` 中观察到：`session/end-seed` 与 `agent/inbox/spliced` 都在 seq 2544，而 `turn/start`=2545 之后连续。被拼接的用户消息作为之后一条已提交的 `user/message`（seq 2548，rpcId 相同）独立留存，因此没有任何用户可见内容是该重复项独有的。手工修复删掉这一条重复行后日志即可加载（4538 个事件）；原始字节备份在日志旁的 `session.jsonl.zstd.corrupt.bak`。

## 提案

给续写的 seq 加跨写入方的栅栏。在提交一个批次前，续写路径在一把每会话目录的独占续写锁（跨进程——`O_EXCL` 锁文件或对日志的建议性 `flock`）下校验该批次的首个 seq 等于磁盘上的已提交事件游标，陈旧的批次从已提交尾部重新推导游标并重新编号，而不是提交一个重复项。恢复在其首次拼接前重新读取已提交尾部以重新推导游标，堵住复用 `session/end-seed` 之前的游标快照的窗口。

配套的加载期恢复让已损坏的会话无需手工重写即可打开：一个中段的重复 seq，若其记录不携带任何独有负载——其消息作为之后一条已提交的 `user/message` 重新出现——则在读取时丢弃它，或由一条 `commitRepair` 式的路径按尾部撕裂路径处理部分末帧的方式处理这一类重复 seq。

## 考虑过的替代方案

- **保持强制失败（当前行为）。** 严格，但一个重复 seq 会让一个本来完整的会话永久无法加载，连同缺口之后的每条消息一起丢失。
- **把整条尾部 +1 重新编号，把重复项保留为独立事件。** 保住了这条多余记录，但之后每个 seq 都要位移，会使其他读取方持久化的游标失效，且毫无收益——该重复项的消息已作为一条已提交的 `user/message` 留存。
- **对每次出现都手工修复。** 修好了一个文件，却留下产生它的并发写入方竞态，损坏会复现。
- **只扩大单进程的部分写入回滚。** 它看不到第二个进程的续写，也看不到 fsync 之后的崩溃；这个重复项是已提交的持久字节，不是它的大小恢复能撤销的尾部撕裂。

## 接受标准

- 两个写入方恢复同一个会话目录，或某次续写在 fsync 与游标推进之间崩溃，都无法在一个 seq 上提交两个事件；陈旧批次被拒绝并从已提交游标重新编号。
- 一个已经含有中段重复 seq 的会话能加载并渲染其聊天历史，无论通过修复路径还是读取时丢弃。
- 包级测试覆盖并发续写、`session/end-seed` 之后的恢复，以及重复 seq 的加载路径；一个无密钥快照钉住修复后会话的转录内容不变。

## 风险

跨进程加锁给每次续写增加一次获取，且不得让接管的常驻运行时与 Web 服务器在同一个会话目录上死锁。读取时丢弃必须在丢弃前证明被丢记录的负载可从之后一条已提交事件完全重建，否则会静默丢数据。修复路径必须把重复 seq（一条多余的已提交记录）与尾部撕裂（一个部分末帧）区分开，以免截断正常的已提交事件。
